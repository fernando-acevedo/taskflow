# 26. Support chatbot: JSON knowledge base and a local intent classifier

- Status: Accepted
- Date: 2026-11-11

## Context

Users who cannot sign in (wrong password, locked account, expired link, email that never arrives) cannot use the app
to ask for help, so the support chatbot must work without a session. It has to answer in English and Spanish, cost
nothing per message and never invent an answer. We do not want an LLM or a cloud service for this: the questions are
few and known, and answers must be reviewed by a person.

## Decision

- **Knowledge base (KB) as JSON in the repo.** One folder: `settings.json`, `synonyms.json`, `common.json` and
  `intents/<Intent>.json`. Every text, label and utterance list holds both locales side by side, so a change to one
  language is reviewed next to the other. Files are embedded in the Infrastructure assembly
  (`Chatbot/KnowledgeBase/**/*.json`, resource name `TaskFlow.KnowledgeBase/<relative path>`).
- **Text variants.** A step's `text` holds 5 variants per locale (`"text": {"en": [...], "es": [...]}`), index 0
  being the reviewed original; quick reply labels stay single strings. The runtime picks one variant uniformly at
  random (20 % each) every time the step is shown (T-141/T-142); `IKnowledgeBase.GetTexts` returns them all and
  `GetText` the first. Variants exist so repeated visits do not read like a script, never to change the meaning.
- **Validator in CI and at startup.** `KnowledgeBaseValidator` (Application, pure) returns every problem with file and
  step context: missing or extra locales, the same number of variants (at least 1) in every locale, empty or
  duplicate variants within a locale, minimum utterances per locale, duplicate utterances, dangling or
  unreachable steps, a placeholder set that is identical across all variants of both locales (and known to
  `settings.links`, also in quick reply urls), repeated quick reply ids, and a blacklist of voseo and
  regionalisms applied to every Spanish variant (the Spanish is neutral). `JsonKnowledgeBaseLoader` runs it and throws one exception listing
  all problems, so a bad KB fails the unit tests and the app does not start.
- **One multilingual ML.NET model.** Text goes through `FeaturizeText` (word and char n-grams) and
  `SdcaMaximumEntropy`, trained on the utterances of both locales at once. Canonical synonyms from `synonyms.json` are
  applied before featurizing so `contraseña` and `password` share a feature. Training and evaluation run in the test
  suite with a per-locale accuracy gate. If a locale falls below the gate, we move to two models (one per locale)
  behind the same interface.
- **Thresholds and session criteria (validated in T0, frozen in `settings.json`).** A prediction is accepted only if
  its score is at least 0.55 (lowered from 0.65 on 2026-11-12 after calibration: 67.6 % answered at 96.1 % accuracy, see docs/analysis/f13-classifier-eval.md) and it beats the second best by at least 0.1; otherwise the bot answers with the
  fallback step, and escalates after 2 consecutive fallbacks (`maxConsecutiveFallbacks`). A session is idle after 30
  minutes (`sessionIdleMinutes`). The language is the UI language when the chat opens and stays fixed for the whole
  session, even if the user types in the other one. The out-of-scope intent is a real class, not only a threshold.
- **Contact links come from configuration.** The texts use `{support}` and `{help}` (also `{help}` as a quick reply
  url). `settings.links` only declares the names, with empty values; the values are `Chatbot:SupportContact` and
  `Chatbot:HelpUrl` (`ChatbotOptions`). Outside Development both are required and validated on start
  (`ValidateOnStart`), so the API does not start without them; Development has example values in
  `appsettings.Development.json`. If `HelpUrl` is empty (only possible in Development) the help button is hidden.
  A placeholder without a value is left visible as `{name}` instead of rendered blank.
- **Frozen KB (T-135).** The reviewed export (13 intents with 48 utterances per locale, 14 flows with 29 steps, 5
  variants per step and locale) was converted once with `backend/tools/chatbot-kb/convert_kb_export.py
  <export-dir> <kb-dir>`, which fails if variant 0 differs from the approved text. `synonyms.json` is maintained by
  hand. From now on the JSON files in the repo are the source: edit them directly and the validator guards them.
- **Scripted dialogue.** Steps with quick replies drive multi-turn conversations; free text is classified again only
  where a step expects text. There is no generated text.
- **Anonymous endpoint.** It has its own rate limit (per IP, separate from `/api/auth`) and a session id generated by
  the server. It never says whether an account or email exists, whatever the user types.
- **Chat data.** Chat entities are excluded from the tenant filter (visitors have no tenant). PII (emails, phone
  numbers, long digit strings) is redacted before anything is stored. A background worker (`ChatRetentionWorker`,
  `Chatbot:Retention:*`: Enabled, Days=90, Interval, BatchSize; one instance at a time through `JobLock`) deletes
  sessions idle for more than 90 days in batches; messages and intent logs go by cascade. Only the session's validated
  locale is persisted, never the one sent on later turns.
- **Startup and tokens.** Outside Development the API does not start when the intent model fails to load (in Development
  it logs a warning and answers with the fallback). `SessionValidationMiddleware` lets `[AllowAnonymous]` endpoints through
  as anonymous when the bearer token is stale, so a signed-out-in-the-background visitor can still chat.
- **No LLM, no cloud services.** Everything runs in the API process.

## Consequences

- Answers are deterministic and reviewable in pull requests; a wrong answer is fixed by editing JSON.
- Quality depends on the utterances: each intent needs at least 30 per locale, written by a person.
- Adding an intent means a new file, no code change; the validator and the accuracy gate catch regressions.
- A single model can favor the language with more data; the per-locale gate makes that visible and the two-model
  fallback is already planned.
- The model is trained in memory at startup (small data); a persisted model is a later optimization if it is slow.
