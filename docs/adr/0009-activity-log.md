# 9. The activity log is recorded explicitly in the handlers, not by an EF interceptor

- Status: Accepted
- Date: 2026-11-05

## Context

Each project needs a history ("who did what and when") for the project and for each task: tasks created, edited,
moved, assigned or deleted; comments; members; labels. Two ways to produce it:

- **An EF Core interceptor** (`SaveChangesInterceptor`, or reading the `ChangeTracker` in `SaveChangesAsync`) that
  turns every added, modified or deleted entity into an entry. It can't be forgotten, but it only sees rows and
  columns: moving a card is a change of `Status` and `Position` plus the renumbering of its neighbors, a label
  change on a task is a row in a join table, and "removed a member" is a deleted `ProjectMember` row. Turning
  that into "moved *Write copy* from To Do to In Progress" needs the domain's meaning back, plus names (task
  title, label name, member) that the interceptor would have to look up while saving. It would also log
  renumbering and other incidental writes, and it has no access to who the user is without more plumbing.
- **Explicit recording in the handlers**, which already know what they are doing and have the values at hand.

## Decision

Handlers record the entry themselves, with `ActivityLog.Record(projectId, type, changes, taskId)` (a scoped service
in Application that wraps `ICurrentUser`, `TimeProvider` and `IAppDbContext`). `Record` only adds the
`ActivityEntry` to the context; the handler's own `SaveChangesAsync` stores it in the same transaction as the change,
so there is never a change without its entry or the reverse.

- `ActivityEntry` (Domain): `Id`, `ProjectId`, `TaskItemId` (nullable), `ActorId`, `Type` (an enum stored as its name),
  `OccurredAt`, `Sequence` and `Changes`, a JSON object in an `nvarchar(max)` column.
- `Changes` holds what the frontend needs to write the sentence, as camelCase keys that depend on the type, and null
  values are left out, except in the `from`/`to` pair of a field change (`title`, `priority`, `dueDate` of a
  `TaskUpdated`), which always has both keys so that setting or clearing a due date shows as a null. Names that can change or vanish (task title, label name) are stored in the entry; user ids are
  stored and the API adds the current display name when it reads (`memberId` gets `memberName`, `assigneeId` gets
  `assigneeName`, `previousAssigneeId` gets `previousAssigneeName`).
- `TaskItemId` has no foreign key, so the entries of a deleted task stay and keep its title in `Changes`.
  `ProjectId` and `ActorId` do have foreign keys with `Restrict`, like the rest of the model.
- `Sequence` is a `bigint IDENTITY` generated by the database. Entries are sorted by `OccurredAt desc, Sequence desc`:
  every entry of one request has the same `OccurredAt`, and a `Guid` v7 id doesn't keep insertion order inside the
  same millisecond, so a reassignment could show before the edit that came with it.
- Indexes `(ProjectId, OccurredAt desc, Sequence desc)` for the project feed and
  `(TaskItemId, OccurredAt desc, Sequence desc)` for the task feed.
- `GET /api/projects/{projectId}/activity` and `GET /api/projects/{projectId}/tasks/{taskId}/activity` need the
  View level and return a page (`page`, `pageSize` up to 100), newest first. The task feed doesn't check that the task
  still exists, so a deleted task's history can be read.
- Only meaningful events are recorded: a task move is recorded when its status changes (not when it is only
  reordered inside a column), an edit only when a field changed, a label update only when its name changed.
- Editing a comment is not recorded: the history says that a comment was added or deleted, and an edit changes
  neither the task nor who takes part in it, so it would only add noise (a typo fix would push real events down
  the feed). If it is needed later, it would be a `CommentEdited` type with `taskTitle` and `commentId`.

## Consequences

- Every new write handler has to call `Record`. Nothing fails if someone forgets; review and the integration tests
  for the existing events are the safety net. It is a line next to the change, in the place where the reader of the
  handler looks.
- Entries describe business events instead of table writes, and the changes carry the old and new values, so the
  frontend doesn't query anything else to render them.
- Writes the interceptor would have caught by accident (renumbering, seeding, admin tools that bypass the
  handlers) are not logged, which is the intent.
- A rename of a task or label doesn't rewrite old entries: they keep the name at the time, like a real history.
- The table only grows. Retention can be added later with a delete by `OccurredAt`.
